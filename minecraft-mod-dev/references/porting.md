# 跨版本和跨加载器维护

## 建立目标矩阵

每个目标使用一行：精确 Minecraft 版本、加载器及版本、API 库、映射（若适用）、JDK/字节码目标、Wrapper/插件、构建命令、运行端、测试状态、产物。只列用户要求的目标。相邻补丁版本也不能自动视为兼容。

先在源版本重现已有构建或记录基线失败，再创建目标适配。保留源版本代码及可用产物，不覆盖原有支持范围。按差异规模采用分支、独立目录或共享核心加加载器适配模块；不要为了少量功能强行引入多模块框架。

## 移植顺序

1. 用目标官方模板核对工具链，先使依赖解析和最小入口工作。不要只改 `minecraft_version`。
2. 比较两端官方迁移说明和依赖源码，定位注册、事件、生命周期、映射与包名差异。
3. 迁移公共玩法逻辑，再适配网络、数据保存、资源和客户端渲染。
4. 验证打包产物及加载元数据，运行各目标的功能测试，记录结果。

数据组件、配方序列化、渲染管线、网络 payload、资源目录命名和注册键要求都是可能的断点；何时发生以及具体 API 必须以目标版本资料为准。旧 MCP/SRG/Yarn/Mojang 命名不能仅做字符串替换；按类型语义及签名对应。对没有传统映射流程的版本，遵从该版本模板。

跨 Forge/NeoForge/Fabric/Quilt 时逐项重审入口、事件、注册、配置、网络、数据能力、访问机制与平台依赖。不要仅替换 import 或 Mod 元数据后就标为完成。

共享核心仅依赖各目标真正共有的接口；平台 API 放到各自模块。资源存在格式差异时分目标生成或维护覆盖层，避免在最终 JAR 中混入另一版本资源。第三方库缺目标版本时说明缺口，评估等价实现或范围调整，不伪造依赖。

## 老版本与快照

旧版先核对归档 MDK、仓库可用性、历史 JDK/Gradle 与构建插件组合。现代注册、JSON 资源或语言格式不能直接倒套到老版本。没有可验证工具链时说明能完成的源码迁移范围，标明构建阻塞。

快照、预发布版及特殊加载器使用确切版本和对应标签；不承诺未来稳定版兼容。游戏版本字符串不能只假定是 `1.x.y`，版本排序与兼容判定使用官方发布信息及加载器规则。

## 验收边界

逐目标构建并独立保留带版本/加载器标识的产物。复用一份 JAR 时必须有对应兼容证据与运行测试；不要仅通过放宽元数据版本范围达成“支持”。

测试至少覆盖该次迁移触及的功能。存档相关改动用旧测试世界副本验证数据读取、保存重进和注册 ID；只成功加载新世界不足以证明旧档兼容。无法提供自动迁移时明确说明，不能静默重置用户数据。

交付矩阵区分“源码已适配”“构建通过”“客户端通过”“专用服通过”和“未验证”。任一目标失败不影响如实交付其他已完成目标，但不得把整个矩阵标为通过。
